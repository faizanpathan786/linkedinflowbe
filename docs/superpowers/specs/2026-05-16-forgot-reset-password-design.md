# Forgot / Reset Password — Design Spec

**Date:** 2026-05-16  
**Status:** Approved

---

## Overview

Add two public, unauthenticated endpoints to the Fastify backend that let users request and complete a password reset. The implementation delegates token generation, storage, and password hashing to better-auth's built-in `emailAndPassword` reset flow, with a custom email sent via the existing Resend integration.

---

## Endpoints

### `POST /api/auth/forgot-password`

- **Body:** `{ email: string }`
- **Auth:** none (fully public)
- **Behaviour:** calls `auth.api.forgetPassword` which generates a verification token, stores it in better-auth's existing `verification` table, and invokes the `sendResetPassword` hook to send the email. Always responds with success regardless of whether the email is registered (prevents email enumeration).
- **Response (always 200):**
  ```json
  { "success": true, "message": "If this email is registered, a reset link has been sent." }
  ```

### `POST /api/auth/reset-password`

- **Body:** `{ token: string, password: string }`
- **Auth:** none (fully public)
- **Behaviour:** maps `password` → `newPassword` and calls `auth.api.resetPassword`. better-auth validates the token against the `verification` table, hashes the new password with scrypt (its internal algorithm), updates the `account` table, and deletes the token row so it cannot be reused.
- **Response (success 200):**
  ```json
  { "success": true, "message": "Password updated successfully." }
  ```
- **Response (invalid/expired token 400):**
  ```json
  { "success": false, "message": "Invalid or expired reset link." }
  ```

---

## Architecture

No new database tables or dependencies are required.

### better-auth internals used

| Internal API | better-auth internal path | What it does |
|---|---|---|
| `auth.api.forgetPassword` | `POST /api/auth/forget-password` | Creates token in `verification` table, calls `sendResetPassword` hook |
| `auth.api.resetPassword` | `POST /api/auth/reset-password` | Validates token, hashes password with scrypt, updates `account`, deletes token |

The Fastify routes (`forgot-password`, `reset-password`) have different path names from the better-auth internal paths (`forget-password`, `reset-password`), so there is no route collision.

## Files Changed

### `src/auth.ts`

Add `sendResetPassword` callback to the `emailAndPassword` config:

```ts
sendResetPassword: async ({ user, token }) => {
  const frontendUrl = process.env.FRONTEND_URL || 'http://localhost:3000';
  const resetUrl = `${frontendUrl}/reset-password?token=${token}`;
  await sendPasswordResetEmail(user.email, user.name, resetUrl);
}
```

The raw `token` is used to construct the frontend URL directly. The `url` param better-auth builds (a backend callback URL) is intentionally ignored.

### `src/lib/email.ts`

Add `sendPasswordResetEmail(email: string, name: string, resetUrl: string): Promise<void>` — an HTML email using the existing LFlow branding (LinkedIn-blue header, CTA button, footer). Uses `process.env.RESEND_FROM` for the sender address.

### `src/routes/auth.ts`

Add two route handlers (no auth middleware):

```
POST /api/auth/forgot-password
  body: { email }
  → auth.api.forgetPassword({ body: { email, redirectTo: FRONTEND_URL + '/reset-password' } })
  → always 200 { success: true, message: "..." }

POST /api/auth/reset-password
  body: { token, password }
  → auth.api.resetPassword({ body: { token, newPassword: password } })
  → 200 { success: true, message: "..." }     on success
  → 400 { success: false, message: "..." }    on invalid/expired token
```

## Token Lifecycle

- **Generated by:** better-auth's `forgetPassword` handler using a secure random verification token
- **Stored in:** better-auth's `verification` table (`identifier = "reset-password:<token>"`)
- **Expires:** 1 hour (better-auth default; configurable via `resetPasswordTokenExpiresIn` in `auth.ts`)
- **Deleted after use:** yes — better-auth deletes the row on successful `resetPassword`

---

## Email

Reset link format sent to the user:

```
https://<FRONTEND_URL>/reset-password?token=<token>
```

The `FRONTEND_URL` env var is already used throughout the codebase. No new env vars required.

## Error Handling

| Scenario | HTTP status | Body |
|---|---|---|
| Email not found | 200 | `{ success: true, message: "If this email is registered..." }` |
| Email found, Resend fails | 500 | forwarded error |
| Token invalid or not found | 400 | `{ success: false, message: "Invalid or expired reset link." }` |
| Token expired | 400 | `{ success: false, message: "Invalid or expired reset link." }` |
| Token already used | 400 | `{ success: false, message: "Invalid or expired reset link." }` |

---

## Security Properties

- Email enumeration is prevented: forgot-password always returns 200 regardless of whether the user exists
- Tokens are single-use: deleted immediately after a successful reset
- Token expiry: 1 hour (better-auth default)
- No new attack surface: both endpoints are stateless wrappers over battle-tested better-auth internals
- Password hashing algorithm (scrypt) is consistent with registration — no algorithm mismatch

---

## Out of Scope

- Rate limiting on forgot-password (can be added later via a Fastify plugin)
- `revokeSessionsOnPasswordReset` (better-auth supports this flag; not enabled in this spec)
- Frontend pages (`/forgot-password`, `/reset-password`) — described in the original request summary but implemented separately in the frontend repo
